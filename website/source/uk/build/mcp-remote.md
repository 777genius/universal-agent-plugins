# Створення пакета віддаленого MCP {#build-a-remote-mcp-package}

**Розробка у збірці з вихідного коду:** команди на цій сторінці потребують
[збірки з увімкненими інструментами розробки](./#build-from-source).
Поточний випуск інсталятора не містить `agentplugins author`.

Оберіть віддалений MCP, якщо сервер уже існує, а пакет має описати з'єднання
агента з ним. Інструменти розробки записують URL, не звертаючись до нього.
Перед передачею пакета користувачам ви маєте з'ясувати вимоги сервісу до
транспорту й автентифікації.

## Явно вкажіть кінцеву точку {#supply-the-endpoint-explicitly}

У прикладах `https://mcp.example.com/mcp` — заповнювач для документації.
Готуючи власний пакет, замініть його реальною кінцевою точкою MCP сервісу.
Команда приймає URL як конфігурацію; вона не перевіряє, чи адреса надає MCP
та чи ваш обліковий запис має доступ.

У збірці з увімкненими інструментами розробки:

```bash
agentplugins author init ./docs-service \
  --template mcp-remote \
  --name docs-service \
  --description 'З’єднання з MCP-сервісом документації команди' \
  --url https://mcp.example.com/mcp
```

Використовуйте ще неіснуюче місце призначення в наявному батьківському каталозі.
Шаблон потребує абсолютного HTTPS URL або HTTP для loopback. Облікові дані,
фрагменти та нерозкриті токени URL не приймаються як параметри шаблону.
Не додавайте пароль до URL.

## Розберіться з файлами {#understand-the-files}

```text
docs-service/
  plugin.json
  mcp.json
  README.md
  .gitignore
```

Кореневий маніфест визначає ідентифікаційні дані пакета. `mcp.json` описує сервер
у `mcpServers`; цей шаблон використовує `type: streamable-http` та наданий URL.
Він не генерує сервер і не додає Skill. Якщо пакет також потребує інструкцій
про те, коли викликати інструменти, скористайтеся [гібридним пакетом](./hybrid).

Перегляньте README й опишіть призначення кінцевої точки, вимоги до облікового
запису та де знайти інструкції з автентифікації. Зберігайте секрети поза пакетом.
URL у файлі, що відповідає стандарту, не доводить доступність сервісу.

## Перевірте конфігурацію та підтримку клієнтів {#check-configuration-and-target-support}

```bash
agentplugins author validate ./docs-service
agentplugins author inspect ./docs-service --target codex,claude
agentplugins author test ./docs-service
agentplugins author compat ./docs-service --target codex,claude
agentplugins author doctor ./docs-service
```

`inspect` може показати компоненти й невиконані вимоги. `compat` оцінює статичну
підтримку адаптерів обраних клієнтів; жодна з команд не потребує їх встановлення.
Doctor не звертається до кінцевої точки.

## Зазначайте невиконану роботу {#keep-the-remaining-work-visible}

Статичні докази автора мають указувати транспорт і потрібні клієнти.
Інсталятор одержувача ще має оцінити політику встановлення та показати інструкції
з активації. Користувачеві може знадобитися вхід, схвалення доступу або новий
сеанс клієнта. Виявлення й виклики інструментів під час виконання потребують
окремих доказів.

Якщо статичні перевірки не проходять, спочатку виправте зафіксовану конфігурацію.
Якщо кінцева точка пізніше недоступна, досліджуйте сервіс або з'єднання клієнта,
а не сприймайте черговий успішний статичний тест як перевірку зв'язку.

Продовжуйте з [тлумачення звітів](./checks) і [передачі планувальнику](./handoff).
