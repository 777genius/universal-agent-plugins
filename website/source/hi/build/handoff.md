# पैकेज इंस्टॉलर योजनाकार को सौंपें {#hand-a-package-to-the-installer-planner}

उपयोगी हस्तांतरण में मानक पैकेज डायरेक्टरी और की गई जाँचों का स्पष्ट विवरण शामिल होता है। प्राप्त करने वाला इंस्टॉलर चुने गए एजेंटों और स्कोप के लिए अपनी योजना बनाता है। सोर्स बिल्ड में पैकेज निर्माण टूल प्रमाण दे सकते हैं, लेकिन प्राप्त करने वाली मशीन पर उनकी आवश्यकता नहीं है।

## पैकेज और प्रमाण तैयार करें {#prepare-the-package-and-evidence}

अस्पष्ट पैरेंट रिपॉज़िटरी के बजाय रूट `plugin.json` वाली डायरेक्टरी चुनें। शामिल करें:

- पैकेज पहचान, संस्करण और सटीक स्रोत रिविज़न या समीक्षा किया स्नैपशॉट।
- सापेक्ष पैकेज रूट और उसके Skills तथा MCP सर्वरों का उद्देश्य।
- टूल संस्करण या सोर्स रिविज़न सहित वैलिडेशन और निरीक्षण परिणाम।
- इच्छित क्लाइंट ID और हर घटक की संगतता के निष्कर्ष।
- रनटाइम पूर्वापेक्षाएँ, प्रमाणीकरण की ज़रूरतें और अभी न जाँचा गया काम।
- कोई भी स्पष्ट रनटाइम परीक्षण, जिसमें चुना सर्वर/टूल और प्लेटफ़ॉर्म हो।

पैकेज संस्करण और CLI संस्करण अलग चीज़ें बताते हैं। उन्हें अलग रखें। साझा निदान में क्रेडेंशियल और अनावश्यक पूर्ण पाथ न दें।

## उपलब्ध हों तो सोर्स पैकेज निर्माण जाँचें पूरी करें {#finish-source-authoring-checks-when-available}

इन वैकल्पिक कमांड के लिए [पैकेज निर्माण की सुविधा वाले सोर्स बिल्ड](./#build-from-source) चाहिए, जो वर्तमान इंस्टॉलर रिलीज़ से अलग है:

```bash
agentplugins author validate ./review-helper
agentplugins author inspect ./review-helper
agentplugins author test ./review-helper
agentplugins author compat ./review-helper --target codex
agentplugins author doctor ./review-helper
```

यह क्रम स्थिर है और पैकेज कोड नहीं चलाता, न ही वास्तविक उपयोगकर्ता की क्लाइंट प्रोफ़ाइल देखता है। किए गए स्पष्ट [MCP रनटाइम परीक्षण](./checks) अलग दर्ज करें। सफल प्रत्यक्ष रनटाइम जाँच भी नेटिव क्लाइंट पहचान या OAuth सिद्ध नहीं करती।

## प्रकाशित इंस्टॉलर से योजना बनवाएँ {#ask-the-released-installer-to-plan}

```bash
agentplugins validate ./review-helper
agentplugins add ./review-helper --target codex --dry-run
```

लोकल स्रोत के लिए भी इंस्टॉलर सुरक्षा मेटाडेटा या अपना पिन किया स्कैनर प्राप्त कर सकता है। उसका वैलिडेशन और dry run ऑफ़लाइन पैकेज निर्माण जाँचें नहीं हैं।

पहली कमांड इंस्टॉलर के पैकेज पढ़ने का प्रमाण देती है। दूसरी Codex चुनकर प्रबंधित बदलाव लागू किए बिना इंस्टॉलेशन का पूर्वावलोकन दिखाती है। दूसरे क्लाइंट के लिए संगतता निष्कर्षों से समर्थित टार्गेट चुनें। प्रोजेक्ट योजना के लिए स्पष्ट `--scope project --project-root /path/to/project` जोड़ें।

पैकेज पहचान, स्रोत, गंतव्य, सुरक्षा निष्कर्ष और बाकी सक्रियण आवश्यकताएँ देखें। लागू करने से पहले लेखक के इच्छित हस्तांतरण से कोई अंतर हो तो हल करें। योजना इंस्टॉल की गई स्थिति की रसीद नहीं है।

## दोहराया जा सकने वाला स्रोत साझा करें {#share-a-reproducible-source}

दूरस्थ वितरण के लिए प्राप्त करने वाला CLI जिस स्रोत को स्वीकार करे, उसका इस्तेमाल करें: हस्ताक्षरित Directory पैकेज, सटीक GitHub स्रोत या समर्थित सीधा Git/आर्काइव स्रोत। सिंटैक्स और उपलब्धता के लिए [इंस्टॉलेशन स्रोत](../use/install) देखें। सटीक बहाली चाहिए तो अपरिवर्तनीय रिविज़न या स्थायी संस्करणयुक्त आर्काइव इस्तेमाल करें। लोकल डायरेक्टरी का अलग, सोच-समझकर स्थानांतरण चाहिए।

सोर्स पैकेज निर्माण CLI पैकेज प्रकाशन, बंडल एक्सपोर्ट या Directory में जमा करने की कमांड नहीं देता। स्रोत होस्ट करना उसे वैलिडेट करने से अलग चरण है। `uap.toml` की निर्भरता घोषणाएँ UAP मैनेजर का अनुबंध हैं; रूट `plugin.json` पोर्टेबल पैकेज की पहचान का प्रामाणिक स्रोत रहता है।

## बाकी काम स्पष्ट करें {#explain-what-remains}

| दिया गया प्रमाण | बाकी काम |
| --- | --- |
| मानक अनुपालन | उपयोगी निर्देश और टूल का सही व्यवहार। |
| स्थिर पैकेज निर्माण जाँचें | रिलीज़ अनुमोदन और सार्वजनिक चैनल की योग्यता। |
| स्थिर क्लाइंट संगतता | वास्तविक नेटिव पहचान और सक्रियण। |
| प्रत्यक्ष MCP रनटाइम जाँच, यदि की गई हो | दूसरे टूल, क्लाइंट, प्रमाणीकरण और न जाँचे परिवेश। |
| इंस्टॉलर dry run | समीक्षा किए बदलाव लागू करना और क्लाइंट सेटअप पूरा करना। |

प्राप्त करने वाला उपयोगकर्ता इंस्टॉल करने के लिए तैयार होने पर [प्लगइन इस्तेमाल करें](../use/install) से आगे बढ़ सकता है। क्लाइंट-विशिष्ट ट्रस्ट और सक्रियण निर्देश पैकेज के साथ रखें।
