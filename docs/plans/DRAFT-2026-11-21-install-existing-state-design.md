## 1. Исходная проблема

`agentplugins add context7` (интерактивно, без `--target`): пользователь проходит выбор
агентов, ждёт, и только потом получает
`foreign: context7 has an unmanaged binding in installation <uuid>; remove it before adding the dependency`
(`environment/coordinator.go:290`). Дефекты: поздно, непонятно (нет клиентов и команды),
«частично установлено» не обрабатывается. (испр.) Проблема шире `add`: та же проверка
блокирует `deps sync` (`deps_apply.go:39,386`), update/management
(`management_plan.go:197`, `management_reconcile.go:92`) и пакетную установку Skills
(`skills_batch_prepare.go:131`). Полный `deps sync` без списка алиасов блокируется одной
unmanaged-привязкой любого пакета. Ошибка без типа, в JSON выходит как `COMMAND_FAILED`.

## 2. Термины

- **Installation** - запись установщика на источник (`SourceKey`); внутри **bindings** по клиентам.
- **Окружение** - `uap.toml` + `uap.lock` + **receipt** на пару (алиас, клиент).
- **Managed** - у binding есть receipt окружения. **Unmanaged** («бесхозная») - binding есть,
  receipt нет (`add --no-save`, старый CLI, `integrations add`, SDK).
- **Нативная запись** - запись в конфиге клиента, неизвестная установщику (руками или другой дистрибутив).
- (испр.) Receipt чужого окружения тоже отображается как «unmanaged» (`observe.go:64-66`), но
  `remove` такую привязку отклонит (`lifecycle_helpers.go:156-160`: «use deps sync for owned
  bindings»). Проверка должна эти два случая различать.

## 3. Инварианты (подтверждены ревью)

1. `docs/UAP_DEPENDENCIES.md` ~383: установка с любым receipt требует авторитета окружения для
   всех привязок, включая новые цели; смешивание imperative-привязки запрещено; окружение не
   может усыновить установку с unmanaged-привязками.
2. `transaction/environment.go:164` `unmanaged installation cannot be adopted`.
   (испр.) **Исключение (`:151-157`): установку без привязок усыновить можно.** Поэтому после
   удаления ВСЕХ unmanaged-привязок saved add работает (данные PLUGIN_DATA сохраняются,
   `remove_prepare.go:73-92`).
3. Проверка `!existing.Managed && existing.SourceKey == pkg.SourceKey` (`coordinator.go:289`) не
   сравнивает клиента: следствие инварианта 1 (pin двойной: уровень installation + `PackageRevision`
   привязки, `domain/state.go:232`; добавление клиента переписывает уровень installation,
   `usecase/installation.go:58-66`).
4. Synс удаляет managed-привязки, которых нет в манифесте (`coordinator.go:179`).
5. `--no-save` не перекрывает receipt окружения.
6. (испр.) Решающая проверка при гонке делается в kernel под `mutation.lock` (`usecase/apply.go:119`),
   а не в coordinator; ранняя проверка в CLI это только подсказка.

Следствие: **per-client состояние «установлено вручную» нельзя показать строкой списка**, пока
инвариант 1 действует. Блокируется пакет целиком. Корректный UI: экран перед выбором агентов.

## 5. Варианты для C

Общая оговорка (испр.): пре-проверке нужен ключ источника, а агентов сейчас выбирают раньше
резолва источника (`saved_add.go:49` и резолв `:80-118`). Для короткого имени ключ до загрузки
Directory неизвестен (`directory:`+DistributionID, `installer/inspect.go:121`). Проверку надо
встраивать в шаг совместимости (`compatibleSavedAddTargets`), сопоставлять по ProductID как
`retainedDirectoryInstallation`, и **переиспользовать правило coordinator, а не копировать его**.
Для проверки достаточно `StateStore.Load` (как `rejectKnownOwnedAdd`); `Inspect` не запускает
нативные пробы, но хеширует деревья (дороже).

### Шаг 0 (общий для всех сценариев, не зависит от решений)
Типизированная ошибка в coordinator: перечисляет ВСЕ клиенты из `U` и installation id и даёт
правильную команду. (испр.) Команда: `agentplugins remove <installation-id> --target codex,cursor`
(через запятую; повтор флага перезаписывает: `target_batch.go:60-69`). Селектор по имени
опасен: неоднозначен при двух дистрибутивах (`read_public.go:208`) и при наличии зависимости
`context7` уйдёт в saved-remove и снимет чужую managed-привязку (`saved_lifecycle.go:36-46`).
Если какой-либо клиент требует внешнего удаления, отказывает вся группа
(`remove_multi.go:190-201`): нужна ветка `--external-uninstalled`. Помогает `add`, `deps sync`,
`update`, JSON. ~80-130 строк + тесты. Надёжность 9, уверенность 8.

### V-A. Остановка до выбора агентов (рекомендую как фазу 1)
Загрузка состояния под загрузчиком, на saved-пути загрузчика сейчас нет
(`saved_add_acquisition.go:89-113`). Если есть `U`, показываем причину и выбор
(испр.: не меню из трёх пунктов, а существующий `Confirm`): «Установить для <S> без сохранения в
uap.toml? [y/N]», причина и команда удаления в Summary; «нет» = отмена. Новых флагов нет.
Оговорки: (а) после перехода на no-save меняется набор доступных клиентов
(`saved_add_acquisition.go:101`); (б) если подходит один клиент, picker не показывается
(`add_application.go:163`); (в) `--no-save` наращивает долг: каждая такая установка добавляет
unmanaged-привязки и потом блокирует saved add/`deps sync` у коллег: сказать это явно на экране.
Надёжность 9, уверенность 8. ~120-200 строк + 100 тестов, 1-1,5 дня.

### V-B. Управляемая замена = «усыновление через переустановку» (фаза 2)
(испр. v3, ПРОВЕРЕНО НА FIXTURE В WORKTREE: ГИПОТЕЗА «remove всех U, затем add» НЕ РАБОТАЕТ)
Ревью предполагало, что исключение инварианта 2 (`environment.go:151-157`, установка без
привязок усыновляема) делает «remove всех `U` и saved add» достаточным. Реальная проверка
показала: после `remove <id> --target codex` (данные сохранены) saved add того же источника
падает с `install cannot change an active revision; use update` (`installer/errors.go:26`,
`ErrUpdateRequired`, «sticky»): остаётся installation без клиентов, привязанная к источнику.
Помогает только `remove <id> --purge-data` (данные удаляются навсегда), поэтому в сообщение
ошибки команда с `--purge-data` НЕ включена. Проверено на fixture, на реальном GitHub-источнике
не проверялось. Следствия: (1) подсказка «remove, затем add» из шага 0 сейчас ведёт в тупик
для пользователя, который остался без привязок: нужно либо чинить sticky-состояние
(усыновление пустой installation или повторное использование её pin), либо менять текст
подсказки; (2) V-B без этого невозможен, это новая работа в ядре установщика, а не склейка
двух существующих команд. Оценка V-B понижена: надёжность 5, уверенность 4, 4-7 дней.

Прежний текст V-B ниже сохранён для истории (он опирался на неверную гипотезу). Ограничения: dry-run `add` до remove
невозможен (PrepareSync откажет, `coordinator.go:288`); императивные add/remove не берут
`environment.lock`; между remove и add клиент остаётся без пакета. Смягчение: сначала
скачать и проверить пакет, затем remove всех `U`, затем add; при сбое add - явный текст и
безопасный повтор (PLUGIN_DATA целы). Не проверено: теряются ли клиентские approvals/auth при
remove+add. Надёжность 6-7, уверенность 6. 3-4 дня + ревью.

### V-C. Усыновление новой операцией
Не нужна при V-B (см. выше); смысл только если нужно без перезаписи файлов. Надёжность 5,
уверенность 4. Ловушка 4 подтверждена: усыновлённые привязки надо вносить в манифест. Сверять
`PackageRevision` каждой привязки. Не рекомендую.

### V-D. Смешанное владение
(испр.) Отклонён: pin двойной, при receipt мутации без authority запрещены
(`transaction/environment.go:19-24`), unmanaged-привязку потом не снять через remove.

### V-E. Только `--no-save` для остальных
Частный случай ответа «да» в V-A. Надёжность 8, уверенность 7.

## 6. Варианты для D (нативная запись пользователя)

Принцип: никогда не перезаписывать молча.
(испр.) Предыдущие утверждения были неверны:
- Атомарности группы нет. Saved add сначала публикует `uap.toml`/`uap.lock`
  (`environmentapp/application.go:99`), затем применяет привязки по одной и не останавливается на

  установки. Это desired-state (следующий `sync` повторит), но пользователю надо сказать прямо.
- Общий read-only контракт уже есть: `clients.RegistryInspector`/`RegistryCollision`
  (`clients/identity.go:21-35`), `NativeIdentityObserver` (`providers/native_identity.go:220-226`),
  `ObservePreparedIdentity`, `ErrForeignNativeIdentity` (`usecase/identity.go:72-80`), уже
  вызывается групповым планированием (`group_plan.go:214`). Новый порт `ForeignEntryProbe` не
  нужен, иначе второй реализации одной задачи. Покрытие неполное: Cursor в user scope возвращает
  Clear (`cursor/identity.go:38-42`), user-lane Cursor вообще не пишет mcp.json
  (`clients/cursor/README.md:45`), пример про Cursor/`mcp.json` для user scope неверен.

Варианты:
- D-1: оставить как есть, но честное сообщение: какие клиенты поставлены, какие нет, что
  записано в манифест. ~60-100 строк. Надёжность 8, уверенность 8.
- D-2: использовать существующий `RegistryInspector` до выбора, строка отключена. Покрытие

  Надёжность 7, уверенность 5.
- D-3: заменить/переименовать с резервной копией: не рекомендую без явного запроса.
