## Explicit policies

1. **Resolution policy.** Ordinary fresh resolution retains the existing minimum-compatible stable policy. Locked install/replay retains exact authoritative pins and never refreshes moving refs. Explicit selected update ranks compatible stable Registry versions descending (then signed release sequence descending). It backtracks within the whole selected graph, respects every existing constraint and eligibility rule, and never silently selects a lower SemVer than an existing pin during explicit update. A compatible old pin is a valid no-change candidate only when it remains eligible under current signed source policy; revoked/suspended releases or new trusted blocking failures cannot be hidden by retaining that pin merely to avoid downgrade. If no eligible permitted candidate remains, refuse explicitly. The no-downgrade rule applies to existing stable package versions (including versioned moving Git/archive plugins); versionless normalized Skills compare immutable commits/tree digests instead. Signed release-channel updates retain their sequence policy and also refuse an explicit stable-version downgrade. During an update, if satisfying the update requires lowering an existing semver package, refuse with a conflict and guidance to change intent deliberately. Newly introduced transitive nodes use the ordinary policy. Existing unselected roots remain pinned; exact commit/version/checksum intent does not move. A signed Registry release selector keeps the existing signed sequence/product/distribution policy rather than becoming a SemVer range. Git branch/tag and mutable archive/web update by immutable source identity; unchanged version text does not hide changed content.
2. **Freshness facts.** Report installed/locked identity, requested selector, available candidate identity and reason through a shared read-only saved-check use case. `pinned` means intentional immutable intent; `current` means a successful check found no permitted identity change; `available` (CLI may preserve established `outdated` spelling) means the same canonical source has a different allowed immutable identity; `check_unavailable` means acquisition/metadata/graph facts could not establish freshness; conflicts/refusals stay explicit. Each result distinguishes selected-root source freshness from overall candidate-graph changes, includes changed shared/transitive closure nodes and their owner edges, and indicates whether the complete requested candidate graph resolved. An unchanged root with a changed dependency closure must never appear as an overall no-op. A failed graph leaves unchecked moving entries unavailable or blocked, never current; exact pins remain pinned with graph diagnostics attached. A freshness result is an observation of source and graph resolution, not approval to apply: preparation still checks ownership, drift, target eligibility, recovery and stale inputs. Never report network failure as current.
3. **Check isolation.** An explicit check uses `dependencyPreviewApp`, temporary acquisition and in-memory/disposable snapshots; it must not write uap.toml, lock bytes, installation state, receipts, managed files, retained data or the persistent package store. Reuse recorded locked facts when safe; acquire verified immutable candidate bytes only as needed. Dispose every candidate on success, failure and cancellation. Passive Management `Inspect` stays network-free and continues to say unchecked/check unavailable until an explicit check response supplies fresh facts; no hidden persisted freshness cache.
4. **Batch selection.** Selected roots/all saved roots resolve in one candidate graph, including their shared dependency closure. Resolve declared aliases to source/node aliases once, deduplicate saved installations and their transitive bindings, and exclude all owned installations from imperative handling. Exact roots are successful pinned no-ops, not candidates for implicit selector changes. `update --all` includes declared but not yet materialized saved roots when intent exists; it preserves one graph, source identity, target scope and ownership boundaries.
5. **Mixed batch order.** Prepare the saved graph in a disposable preview, prepare every imperative installation with online host preparation disabled or redirected to disposable roots, and validate saved/imperative stale-input guards before any durable effect. Preflight refusal applies nothing. Apply the saved environment first using its existing receipts/recovery semantics, then imperative installations in stable order. Recheck an imperative operation just before its effects using existing boundaries; any failure after effects reports actual partial/failed/not-attempted rows and recovery guidance. Do not promise global atomicity. Current `prepareUpdateMany` permits online host preparation through `OnlinePreview`; merely reusing its existing real-update options would violate this preflight boundary. Preserve required host eligibility and retained preparation through the existing preview/prepared-host seams, with final real host preparation only after the complete preflight succeeds. A persisted saved candidate plus incomplete materialization is reported as such, not success. Cancellation before apply changes nothing; cancellation during effects follows existing authoritative outcomes and stops remaining operations.
6. **Source retention and no-op.** Updates never switch canonical repository/path/product/distribution or silently rewrite exact intent. Preserve unchanged manifest/lock bytes. Pinned and truly current no-ops do not rewrite locks or persistent store. Existing source-switch refusal, unselected pin verification, stale prepared plans, activation/auth readiness and partial-retry recovery remain mandatory.
7. **API boundary.** Add one explicit authenticated read-only `POST /api/v1/environment/check-updates` operation with optional selected declared aliases/all and a typed response of per-entry facts/diagnostics. Reuse Management selection/context validation, backend interface and OpenAPI generation conventions. Selection reuses existing Update request limits and validation: explicit unique nonempty aliases or `all: true` required; reject aliases plus all, empty selection, duplicate/invalid aliases or oversized input as invalid request; unknown or transitive-only aliases use existing `DEPENDENCY_NOT_DECLARED` refusal. `all: true` with no declared roots succeeds with an empty result. One failed source check or graph conflict means the complete request is unavailable/blocked with safe overall and per-entry diagnostics; retain independently known pinned facts but do not present an incomplete candidate as approved/current. Source-check failure is a typed check result; malformed/context/selection requests retain established HTTP errors. CLI uses existing diagnostic/failure conventions, never changes a failed check into current. Cancellation propagates the context error, discards disposable results, and changes nothing. No mutation operation ledger, asynchronous job or cache is needed for this bounded request. Client cancellation stops this read-only request. Ordinary inspection stays passive. Add only a thin TypeScript SDK method and generated contract artifacts required by the schema; do not publish an SDK release. Populate existing plan `fromVersion`/`toVersion` from authoritative observed/locked facts and show minimal useful CLI before/after identities, including commit/digest when version labels are empty or equal.
