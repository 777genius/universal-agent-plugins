## Explicit policies

1. **Resolution policy.** Ordinary fresh resolution retains the existing minimum-compatible stable policy. Locked install/replay retains exact authoritative pins and never refreshes moving refs. Explicit selected update ranks compatible stable Registry versions descending (then signed release sequence descending). It backtracks within the whole selected graph, respects every existing constraint and eligibility rule, and never silently selects a lower SemVer than an existing pin during explicit update. A compatible old pin is a valid no-change candidate; if satisfying the update requires lowering an existing semver package, refuse with a conflict and guidance to change intent deliberately. Newly introduced transitive nodes use the ordinary policy. Existing unselected roots remain pinned; exact commit/version/checksum intent does not move. A signed Registry release selector keeps the existing signed sequence/product/distribution policy rather than becoming a SemVer range. Git branch/tag and mutable archive/web update by immutable source identity; unchanged version text does not hide changed content.
2. **Freshness facts.** Report installed/locked identity, requested selector, available candidate identity and reason through a shared read-only saved-check use case. `pinned` means intentional immutable intent; `current` means a successful check found no permitted identity change; `available` (CLI may preserve established `outdated` spelling) means the same canonical source has a different allowed immutable identity; `check_unavailable` means acquisition/metadata/graph facts could not establish freshness; conflicts/refusals stay explicit. A freshness result is an observation of source and graph resolution, not approval to apply: preparation still checks ownership, drift, target eligibility, recovery and stale inputs. Never report network failure as current.
3. **Check isolation.** An explicit check uses `dependencyPreviewApp`, temporary acquisition and in-memory/disposable snapshots; it must not write uap.toml, lock bytes, installation state, receipts, managed files, retained data or the persistent package store. Reuse recorded locked facts when safe; acquire verified immutable candidate bytes only as needed. Dispose every candidate on success, failure and cancellation. Passive Management `Inspect` stays network-free and continues to say unchecked/check unavailable until an explicit check response supplies fresh facts; no hidden persisted freshness cache.
4. **Batch selection.** Selected roots/all saved roots resolve in one candidate graph, including their shared dependency closure. Resolve declared aliases to source/node aliases once, deduplicate saved installations and their transitive bindings, and exclude all owned installations from imperative handling. Exact roots are successful pinned no-ops, not candidates for implicit selector changes. `update --all` includes declared but not yet materialized saved roots when intent exists; it preserves one graph, source identity, target scope and ownership boundaries.
5. **Mixed batch order.** Prepare the saved graph in a disposable preview, prepare every imperative installation, and validate saved/imperative stale-input guards before any durable effect. Preflight refusal applies nothing. Apply the saved environment first using its existing receipts/recovery semantics, then imperative installations in stable order. Recheck an imperative operation just before its effects using existing boundaries; any failure after effects reports actual partial/failed/not-attempted rows and recovery guidance. Do not promise global atomicity. A persisted saved candidate plus incomplete materialization is reported as such, not success. Cancellation before apply changes nothing; cancellation during effects follows existing authoritative outcomes and stops remaining operations.
6. **Source retention and no-op.** Updates never switch canonical repository/path/product/distribution or silently rewrite exact intent. Preserve unchanged manifest/lock bytes. Pinned and truly current no-ops do not rewrite locks or persistent store. Existing source-switch refusal, unselected pin verification, stale prepared plans, activation/auth readiness and partial-retry recovery remain mandatory.
7. **API boundary.** Add one explicit authenticated read-only `POST /v1/environment/check-updates` operation with optional selected declared aliases/all and a typed response of per-entry facts/diagnostics. Reuse Management selection/context validation, backend interface and OpenAPI generation conventions. No mutation operation ledger, asynchronous job or cache is needed for this bounded request. Client cancellation stops this read-only request. Ordinary inspection stays passive. Add only a thin TypeScript SDK method and generated contract artifacts required by the schema; do not publish an SDK release. Populate existing plan `fromVersion`/`toVersion` from authoritative observed/locked facts and show minimal useful CLI before/after identities.
