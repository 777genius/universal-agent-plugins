## Source-backed triage and narrowly scoped action plans

### A. Copilot disabled native setting after uninstall: BUG-019 / BUG-035

Reproduced **23/23** completed Copilot plugin removals with `cleanup-failed`: UAP `list` empty and `remove` exit 0, but native `.copilot/settings.json` retained one exactly qualified `enabledPlugins` entry. The read-only, credential-free structured proof was **identical in all 23 cases**:
- `before`: native file absent.
- `after_add`: one exact managed `identity@agentplugins-<12 hex>` key, value `true`.
- `after_remove`: same qualified key, value **`false`**; **zero true** keys. The foreign sentinel and repeat-add oracles passed.

**Interpretation:** we have observed *disablement with a retained configuration key*, not an active registration; nevertheless, strict removal currently fails and these **remain 23 non-PASS**. No raw client settings, arbitrary keys, provider secrets or files outside the disposable profile were exported. Next: confirm official native Copilot 1.0.105 semantics and whether the `false` value is deliberate; only then choose between an **exact-owned narrow deletion** in the existing adapter (with foreign/ownership regression) or an independently justified non-active-residual oracle. Never broadly rewrite native settings or report these as PASS on current evidence. See [BUG-019](bugs/BUG-019-copilot-native-settings-cleanup.md) and [BUG-035](bugs/BUG-035-copilot-enabledplugins-value-evidence.md).

### B. Kimi 2.3.2 project Skill source plan refuses all 30: BUG-030 follow-up

The current workflow now installs **actual `@moonshot-ai/kimi-code@2.3.2`** for Skills, unlike the prior unqualified 2.4.1. The case performs a genuine isolated `git init --quiet` before add; the positive genuine Kimi `--version` probe reports **2.3.2**. Nevertheless, all **30/30 distinct GitHub Skills** return `PLAN_REJECTED` with `candidates: []` and **no managed registrations**, rather than source success. This *invalidates the earlier hypothesis that version and Git-root preconditions suffice*. No profile contamination or user data mutation is visible. Exact underlying cause is still obscured by the generic `skillsCatalogSession.reviewRefusal` fallback.

**Narrow next step:** add a **redacted, strictly allowlisted read-only internal failure-stage diagnostic** to the disposable live lane (or an opt-in test-only counterexample fixture); confirm Go `DetectedClient` executable/version/root admission versus npm's resolved `dist/main.mjs` executable, nearest-Git selection, ownership/collision, and planner preflight. Only then change the smallest responsible component; keep public provider-origin errors secret and preserve the native 2.3.1/2.3.2 allowlist. Do not accept the unreviewed 2.4.1 to force a PASS. See [BUG-030](bugs/BUG-030-kimi-project-skill-native-fixture.md).
