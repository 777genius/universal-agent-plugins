# Agentplugins stable release

This runbook is for maintainers. An explicit owner request to make or publish a
release authorizes choosing and publishing the next suitable unused version
within the same product and channels, subject to the owner's explicit constraints.
Report the chosen version; do not ask again solely for version selection or
skipping a cancelled, never-public candidate. Preparation, review, and draft-only
requests do not authorize public publication. All release gates below still apply.
This repository owns both the binary release and the separate npm facade
publication workflow, which updates `latest`. Draft qualification defaults to
non-public; public publication requires the owner release authorization above
and `publish_release=true` (or the explicit `auto_publish=true` chain).
`777genius/plugin-kit-ai` is the historical GitHub rename alias for
`777genius/universal-agent-plugins`, not an independently owned producer.
Existing immutable producer identity checks retain that historical slug.

## Required gates

- The release tag matches `agentplugins-vX.Y.Z` and freezes an approved commit
  on `main`. Descendant commits on `main` do not invalidate that candidate.
  Moving its tag or removing its ancestry from `main` still refuses promotion.
- Required CI, CodeQL, dependency review, and vulnerability checks are green.
- For each required check, including dependency review, the release workflow
  accepts success on the tagged commit or an associated merged PR head. A
  merged PR is not required when the exact commit has every required check. This
  fallback is the executable workflow behavior; owner release review still
  requires final exact-commit evidence. Direct pushes run dependency review
  against the preceding push SHA; missing comparison bases fail closed.
  Repository settings are not treated as the release proof.
- The release-bound Directory bootstrap passes the workflow check: snapshot,
  envelope, trusted keys, generated bytes, expected signing identity, and
  validity at release time. This does not establish package runtime support.
- `agentplugins-release` requires a reviewer and permits `main` and the
  `agentplugins-v*` tag deployment pattern. Dispatch with `--ref <exact-tag>` so
  the workflow source stays pinned even when `main` advances. The source guard
  rejects a different workflow revision, a different tag, or a non-main ancestor.
  Keep the environment reviewer requirement; adding the narrow tag pattern does
  not authorize unreviewed deployments.
- This workflow has one agentplugins-only dispatch contract. It qualifies a
  draft by default and publishes only with `publish_release=true`; promotion
  then auto-dispatches `agentplugins-npm-publish.yml` in this same repository
  against the same tag, so the npm facade cannot be forgotten after the GitHub
  release goes public.

The checked-in npm version `0.0.0-development` is intentional. Staging derives
the publishable version from the approved tag; do not manually bump it.

## Release-preparation pull requests

During an owner-authorized release, a pull request that only prepares the
release and changes no executable behavior is merged as soon as it is
mergeable, without waiting for its own CI. This covers release notes, the
changelog, documentation and version references in non-executable metadata.
Do not park the release on such a pull request.

This does not relax any release gate. The candidate commit on `main` still needs
every required check green before the tag is created, and qualification and
promotion run unchanged. A pull request that touches code, workflows, release
scripts, generated files, dependencies or the Directory bootstrap is not covered
and follows the normal review and CI path.

## GitHub assets

1. Create the approved annotated stable tag on current `main` and push only that
   tag.
2. Finalize release notes before qualification. Dispatch `Agentplugins Release Assets`
   with `--ref <exact-tag>`, the exact tag and the optional final `release_notes`
   prefix. Leave the typed boolean `publish_release=false` (the default) for
   draft-only qualification. If the owner authorized public publication, set
   `auto_publish=true` to chain promotion automatically: once every draft proof
   passes, the run dispatches promotion, which waits for and authenticates the
   finished qualification run.
   All environment reviews still apply. Do not edit draft notes or assets after
   qualification: metadata changes deliberately invalidate the frozen receipt.
3. Review the frozen commit and approve the `agentplugins-release`
   environment deployment. This initial technical review is required even for
   draft-only runs; it does not authorize public version publication.
4. Confirm the workflow attests all six binaries, `checksums.txt`,
   `release-manifest.json`, and `THIRD_PARTY_NOTICES.txt` before creating the
   non-public draft. The four Linux and Windows binaries come from `build`. The
   two macOS binaries come only from `sign-macos` (see
   [macOS signing and notarization](#macos-signing-and-notarization)), and
   staging refuses unless their SHA-256 equals what that job signed and
   notarized. Checksums, the manifest, attestations, npm pins and every proof
   therefore see the signed macOS bytes.
5. Confirm the read-only platform-proof workflow receives the same-run frozen
   asset artifact and succeeds on all six native targets. For a draft it cold
   bootstraps the npm launcher from the exact local asset only after matching
   the embedded filename, size, and SHA-256; no GitHub token reaches the
   launcher or released binary. It then proves a warm-cache invocation with
   the local proof source removed. The standard authoring journey must
   succeed on every target except `darwin-amd64`: its packageview source
   adapter is unavailable there, so that proof asserts a fail-closed
   `platform_unavailable` result (no files written) instead of success.
   Until the matrix aggregates successfully, no public GitHub Release may
   exist.
6. Confirm the reusable Hermes and Antigravity native workflows succeed. They
   start after `stage-draft`, in parallel with `platform-proof`. Each uses the
   same-run complete nine-asset artifact from `stage-draft`, with the exact frozen checkout and `checksums.txt` SHA-256.
   `release-assets.js` verifies the full bundle before the selected binary runs;
   source compilation is disabled for these release lanes. The existing real
   Hermes 0.23.0 and `agy` 1.5.3 lifecycle harnesses run on Linux amd64, macOS
   arm64 and Windows amd64. Each client aggregate requires exactly these three
   passing receipts, with no duplicate or mixed source/run/asset identities.
   Receipts bind the filename, size, binary SHA-256 before and after execution,
   actual UAP version, manifest/checksums digests, harness hashes, vendor pin,
   launcher/runtime hashes, vendor version and transcript SHA-256. Receipts and
   transcripts are retained as same-run artifacts for 14 days; a pass receipt
   is written only after successful native execution. GitHub/npm credentials
   are removed from the environment before the client or released binary runs.
   These three vendor platforms supplement the six mandatory UAP platform
   proofs; they do not establish six-platform vendor support or Antigravity
   IDE activation.
7. Confirm `verified-draft` succeeds after all six UAP proofs and both new-client
   aggregates, reverifying the live
   draft identity, manifest, all nine assets, and attestations, and uploads
   `verified-draft.json`. With `publish_release=false`, promotion is skipped
   in this run. With `auto_publish=false`, the verified draft remains non-public.
   Schema2 receipts also bind the exact npm artifact ID, ZIP SHA-256, tarball
   filename, SHA-512 SRI and SHA-1 already exercised by all six native jobs.
8. When the owner request authorizes publication,
   dispatch the existing producer with `publish_release=true`, plus
   `qualified_run_id` and `qualified_run_attempt` from the successful
   `publish_release=false` run; use `--ref <exact-tag>`. With `auto_publish=true`,
   the qualification run dispatches this phase for you as soon as every
   platform and native proof has passed, in parallel with `verified-draft`. The
   promotion run waits in the tag-keyed concurrency group until the qualification
   run finishes and refuses unless that run completed successfully with a
   successful `verified-draft` and its receipt. The frozen
   tag/source-ref/`main` ancestry and required commit gates still run. Promotion authenticates the prior successful
   draft-only workflow attempt, all six native platform proofs, both successful
   Hermes/Antigravity aggregate jobs (including every aggregate step), its verified
   receipt artifact and ZIP SHA-256, then compares that receipt with a fresh
   verification of the live nine-asset draft and attestations. Approve the
   promotion environment deployment only after this check succeeds. The job
   repeats the same verification immediately before publishing by the verified
   numeric release ID, then confirms that the tag still resolves to that ID.
   It does not rebuild binaries or rerun native platform proofs.
   If `verified-draft` fails in an `auto_publish=true` run, the promotion run
   that was already dispatched cannot publish: it fails closed by itself once it
   leaves the queue. Still cancel it manually before re-running qualification.
   Otherwise the new attempt of the same qualification run queues behind it in
   the tag concurrency group, and its `gh run watch` can wait until timeout.
   Re-run failed jobs does not dispatch promotion again, so after fixing and
   requalifying, dispatch promotion by hand as described in this step. The same
   applies if you cancel qualification manually after the proofs passed: the
   dispatched promotion run remains queued and must be cancelled too.
9. After authorized promotion, verify the resulting public release contains six platform binaries,
   `checksums.txt`, `release-manifest.json`, and `THIRD_PARTY_NOTICES.txt`, and
   verify GitHub attestations for every file, including the notices.
   This exact stable public release is the immutable producer handoff consumed
   by this repository's separate UAP npm facade workflow.
   A standalone public-release platform proof continues to prove the normal
   anonymous GitHub release download without changing publication ownership.

The workflow rejects every existing public release. A draft-only rerun accepts an
existing draft only when its tag, frozen commit, draft status, complete asset
set, and every asset byte exactly match the rebuilt release; it never uploads
over an existing asset. Signed macOS binaries are not byte-reproducible: every
signature carries a new Apple timestamp. Use Re-run failed jobs in the run that
created the draft; it reuses the signed artifact. A new dispatch or Re-run all
jobs re-signs, so `stage-draft` refuses the existing draft; an owner then
verifies it was never public, deletes only that draft (not the tag) and
qualifies again. Promotion requires an unexpired receipt artifact from
the exact successful draft-only run attempt. A failed native proof intentionally
leaves that exact draft non-public. Fix the proof defect and rerun the same tag
to qualify it. If draft
creation itself was interrupted and left an incomplete or non-matching draft,
an owner must verify that it was never public, delete only that draft release
(not the tag), and rerun. Never edit or replace assets in place.
Every dispatch still requires the exact frozen tag/workflow-source gate and
proves that the candidate remains an ancestor of current `main`. Only descendant
movement of `main` is allowed; candidate bytes and required checks never float.
A workflow-dispatch ref of current `main` still has to equal the candidate SHA.

Go and source npm qualification run in parallel with the binary build. One
`build` job embeds the Skills picker bundle once and cross-compiles all six
binaries sequentially, then refuses unless exactly six were produced.
`sign-macos` signs and notarizes the two macOS binaries after `build`. Draft
staging requires all three lanes and `sign-macos`. Go compilation/dependency caching is
allowed, while `-count=1` forces the release's Go tests to execute. Staged npm
contract tests, all six native platform proofs and both three-platform
Hermes/Antigravity release-native aggregates remain mandatory. Publication
reuses their exact archived npm tarball instead of staging, testing and packing
it again. Only postpublish signature/provenance and real registry lifecycle
checks are deferred until the package is public.

Current producer promotion passes the narrow `--require-hermes-antigravity`
option at both archived-receipt verification calls. It requires the exact two
new aggregate job names to succeed; missing, failed, skipped, cancelled or
incomplete aggregates refuse promotion. The producer's immutable verified-draft
receipt and existing nine-asset authority remain unchanged. Historical receipt
schemas and callers that audit older releases retain their original contract.

For a schema-v1 historical platform audit, dispatch `Agentplugins Platform
Proof` with `--ref <exact-tag>` and `allow_legacy_manifest=true`. The workflow
must already exist at that tag, and its source SHA must equal the audited tag
commit; current `main` is never allowed to impersonate a historical harness.

## macOS signing and notarization

The `sign-macos` job runs on a GitHub-hosted `macos-15` runner after `build`
and before `stage-draft`, in the `macos-signing` environment. It runs
`scripts/sign-agentplugins-macos.sh`, which:

- imports the Developer ID Application certificate into a throwaway keychain
  with a random password, takes the signing identity from that certificate,
  and deletes the keychain and decoded key files on every exit path;
- signs both macOS binaries in place with `codesign --force --options runtime
  --timestamp --identifier com.777genius.agentplugins`. `--force` replaces the
  ad-hoc signature the Go linker adds to darwin/arm64 binaries. The x86_64
  binary is signed on the Apple silicon runner without running it;
- verifies `codesign --verify --strict`, the Developer ID Application
  authority, `TeamIdentifier` equal to `APPLE_TEAM_ID` and to the pinned release
  team `86399583GS`, the hardened runtime flag and a secure Apple timestamp;
- notarizes one zip with both binaries through `xcrun notarytool submit --wait`
  (30-minute wait limit, 45-minute job limit), requires `Accepted`, and requires
  that the notary log ticket covers each binary's CDHash;
- runs a quarantined copy of the native arm64 binary (`version`) with an empty
  environment. It must print the release version. This proves the hardened
  runtime does not break the CLI; it is also a Gatekeeper check only when the
  runner has assessments enabled, which `gatekeeper-status.txt` records. The
  notarization proof is the `Accepted` status and the CDHash binding;
- uploads `agentplugins-darwin-signed` for staging and the
  `macos-notarization-evidence-<attempt>` artifact (90 days): the notary
  submission and log, `codesign -dv` output, informational `spctl` output and
  `signing-summary.json` with the CDHash and SHA-256 of each binary.

`spctl` output is evidence only, not a release condition. Promotion and npm
publication also authenticate that `sign-macos` succeeded, with every step, in
the qualification run. A missing, failed, skipped or cancelled `sign-macos`
leaves `stage-draft` and every later mutating job unreachable.

### Setup

The `macos-signing` environment holds exactly six secrets: `APPLE_CERTIFICATE`
(base64 `.p12` with the Developer ID Application certificate and key),
`APPLE_CERTIFICATE_PASSWORD`, `APPLE_TEAM_ID`, `APPLE_API_KEY_BASE64` (base64
App Store Connect `.p8` key), `APPLE_API_KEY_ID` and `APPLE_API_ISSUER`. Its
deployment policy allows only the `agentplugins-v*` tag pattern, so dispatch
with `--ref <exact-tag>`; a run from `main` cannot reach the secrets and fails
closed at `sign-macos`. No other job references these secrets, and the workflow
has no `pull_request` trigger. Rotate the secrets before the certificate
expires; an expired or revoked certificate fails `sign-macos` and blocks the
release until it is replaced.

### What users get

Notarization means Apple scanned these exact binaries and issued a ticket keyed
by their CDHash. A bare Mach-O cannot be stapled (`stapler` accepts only app
bundles, disk images and installer packages), so the ticket stays with Apple.
When a quarantined file runs, for example a browser download from the release
page, Gatekeeper fetches the ticket online and allows it without a warning.
Offline, a first launch of a quarantined download can still be blocked. Downloads
by `install.sh`, `curl`, the npm launcher or Homebrew are not quarantined, so
Gatekeeper does not assess them; the kernel still enforces the valid Developer
ID signature. Windows binaries stay unsigned (there is no Authenticode
certificate) and, like the Linux binaries, are covered by checksums and GitHub
artifact attestations only.

### Verify a signed release

```bash
gh release download agentplugins-vX.Y.Z --repo 777genius/universal-agent-plugins \
  --pattern 'agentplugins_X.Y.Z_darwin_arm64'
codesign --verify --strict --verbose=2 agentplugins_X.Y.Z_darwin_arm64
codesign -dv --verbose=4 agentplugins_X.Y.Z_darwin_arm64
spctl -a -vv -t install agentplugins_X.Y.Z_darwin_arm64
```

`codesign -dv` must show `Authority=Developer ID Application: ... (86399583GS)`,
`TeamIdentifier=86399583GS`, `flags=0x10000(runtime)`, a `Timestamp=` line and
`Identifier=com.777genius.agentplugins`. `spctl -t install` reports
`accepted` and `source=Notarized Developer ID` when the ticket is reachable
(`spctl -t exec` rejects any bare command-line tool as "not an app"). The
qualification run's `macos-notarization-evidence-<attempt>` artifact has
`notary-log.json` with `"status": "Accepted"` and a `ticketContents` CDHash
equal to the `CDHash=` line of `codesign -dv`.

### One-time identity check

Before the first signed release, a maintainer runs the same script locally on
macOS with Xcode command-line tools:

1. Build the two binaries:
   `mkdir -p "$TMPDIR/uap-sign/bin" && cd cli && for arch in amd64 arm64; do GOOS=darwin GOARCH=$arch CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=0.0.0" -o "$TMPDIR/uap-sign/bin/agentplugins_0.0.0_darwin_$arch" ./cmd/agentplugins; done`
2. Load the six secret values into the current shell only (for example with
   `read -rs`), never into shell history or files.
3. Run `bash scripts/sign-agentplugins-macos.sh agentplugins-v0.0.0 "$TMPDIR/uap-sign/bin" "$TMPDIR/uap-sign/evidence"`.

It must end with `darwin_amd64_sha256=` and `darwin_arm64_sha256=` lines.
This exercises the `.p12` import, the identity, signing, the notary API key,
the CDHash binding and the quarantined run exactly as CI does, and submits the
test binaries to Apple. The script temporarily adds the throwaway keychain to
the user keychain search list and restores it on exit. If it is killed, check
`security list-keychains -d user` and delete the leftover
`agentplugins-macos-signing.*` keychain with `security delete-keychain`.

## Third-party notice delivery

New release preparation copies `npm/agentplugins/THIRD_PARTY_NOTICES.txt` into
an identically named companion release asset. It is included in `checksums.txt`,
attested, compared on draft reuse, and reverified before promotion. The six raw
binary filenames, bytes, download URLs, and schema-v2 binary manifest stay the
same. The checksum list gains one notice entry. Historical releases without the
companion remain readable; this does not qualify their notice delivery.

The npm file list includes the complete notice text even with pack scripts
disabled. Its checked-in copy must match
`cli/THIRD_PARTY_NOTICES.txt`; the npm tests enforce this in the
source tree. When updating production dependency notices, copy the canonical
file to the npm package too. Staging requires the verified companion before any
staging mutations and checks the npm copy against it. Historical releases without
the companion remain readable by the verifier but cannot be staged for npm.
The npm tarball still contains no native binaries.

Native users must download and retain `THIRD_PARTY_NOTICES.txt` from the same
release alongside their binary, and include it when redistributing. Release
notes state this requirement. Raw-binary bootstrap and atomic installation do
not fetch the companion automatically. Homebrew and other downstream packagers
must arrange notice delivery themselves; this change does not prove that they
do. Companion availability does not guarantee delivery to a user who downloads
only a binary. The existing notice inventory covers the terminal integration;
this packaging change is not an audit of every historical dependency license.

## Homebrew tap

Homebrew synchronization is owned by
[`777genius/homebrew-agentplugins`](https://github.com/777genius/homebrew-agentplugins),
not by a cross-repository token in this source repository. Its `Sync
Agentplugins release` workflow checks the latest stable release every hour and
can also be dispatched with one exact `agentplugins-vX.Y.Z` tag.

The tap downloads only the exact public `release-manifest.json`, requires the
stable tag to resolve to the embedded source commit, verifies the GitHub
artifact attestation, and generates `Formula/agentplugins.rb` from the six
closed-set asset identities. The formula exposes the four macOS and Linux
assets and pins every URL to its release tag and SHA-256. Synchronization uses
the tap repository's short-lived `GITHUB_TOKEN`, is idempotent, and does not
require a long-lived cross-repository PAT. If automatic synchronization fails,
fix or manually dispatch the tap-owned workflow with the same immutable release
tag. Do not edit a released formula by hand or repoint it to different bytes
under the same version.

## Producer cutover and npm publication

The historical `plugin-kit-ai` producer slug identifies this same repository. The
release workflow builds, attests, draft-proves, and verifies the same six assets
plus `checksums.txt`, `release-manifest.json`, and `THIRD_PARTY_NOTICES.txt`.
It promotes only with explicit `publish_release=true` after all existing gates.
The npm facade is staged from
the exact frozen binary assets during draft proof and never embeds the binaries
in its tarball. Publication reuses those tested bytes after promotion.

`.github/workflows/agentplugins-npm-publish.yml` is the trusted publisher. The
promote job of `agentplugins-release.yml` dispatches it automatically from the
exact `agentplugins-vX.Y.Z` tag with `publish=true` and the authenticated
`qualified_run_id` / `qualified_run_attempt`; dispatching it manually the
same way is the documented recovery path when a publish run is cancelled or
fails. The scheduled `agentplugins-npm-drift.yml` guard warns on a mismatch
inside a six-hour publication window (long enough to cover the human
`npm-agentplugins` approval) and fails once npm `dist-tags.latest` stops
matching the newest public release beyond that window. The
prepare job requires a public, immutable GitHub release, verifies every asset
and GitHub attestation, authenticates the completed qualification and its
schema2 receipt, and downloads its exact npm artifact by ID and ZIP digest.
It checks the public release still has the qualified asset identities, verifies
the tarball SRI/SHA-1, and uploads those same bytes to the publish job. It never
repacks or substitutes an archive from a different source/run/attempt. The publish job runs in the protected `npm-agentplugins` environment,
requires GitHub OIDC (`id-token: write`), refuses `NPM_TOKEN` and
`NODE_AUTH_TOKEN`, and publishes with npm provenance. The final job verifies
public metadata, SLSA provenance, npm audit signatures, the tarball digest, and
an isolated `codex,cursor,kiro` add/info/update/remove lifecycle plus an
OpenCode repair check against an immutable registry package.

With `publish=false`, only the immutable prepare checks run; no npm state is
changed. A published version is never overwritten and a stable tag is never
reused. If the package disappears from npm, registry preflight fails closed;
investigate before another release attempt. The workflow never recreates an old version
or a missing package, and never uses a bootstrap token. A new workflow cannot
reuse a historical schema1 receipt for npm publication; use the workflow at that
historical tag for historical recovery.

Never publish an empty placeholder, reuse a tag, overwrite release assets, or
resolve a binary through an unpinned GitHub `latest` release.

## Release pipeline rehearsal

`Release pipeline rehearsal` runs on relevant pull requests and can be manually
dispatched without creating tags, drafts or registry versions. It exercises the
actual source guard, receipt verification and exact-tarball reuse path using
throwaway Git repositories, real npm archives and a read-only GitHub API fixture.
Negative controls cover missing/failed qualification jobs, changed tags or
artifacts, stale attempts, archive traversal and changed public asset identities.
This tests orchestration and custody, not new real-client/runtime qualification.

### Production site source activation

Both Pages publishers select `website/production-source.json` before installing
build tools. The accepted immutable commit/tree keeps CLI source changes separate
from public site activation while signed feeds continue refreshing normally.
Advance this pin only after reviewing the selected site source and qualifying its
public client capabilities against the actual published stable npm CLI. Manual
Pages `expected_sha` still identifies the workflow/control commit. The final
`BUILD_PROVENANCE.json` records both commits, the source tree, pin digest and
mirrored feed marker digest. Source or release checks fail closed; no fallback
source or alternative feed publisher is used.
